# MCP protocol revision 2026-07-28: what it changes for `bin/adr-mcp`

Research note for TASK-58. Every fact below is verified against a primary source: the
normative specification pages on `modelcontextprotocol.io`, and the authoritative JSON
schema plus reference implementation shipped in the official Python SDK `mcp` 2.0.0
(`modelcontextprotocol/python-sdk`, tag `v2.0.0`, released 2026-07-28, MIT).

The SDK is used here as a **reading reference only**. adr-kit keeps its own
dependency-free server; see the ADR for that decision.

## 1. The one-sentence version

The protocol became stateless: `initialize` and `notifications/initialized` are gone, and
every request now carries its own protocol version and client capabilities in `params._meta`.

## 2. The two eras

The SDK's version registry (`src/mcp-types/mcp_types/version.py`) draws the line that
matters for a dual-era server. It is an enumerated set, not an ordered scalar — the file
warns explicitly that date-shaped strings only *happen* to sort lexicographically and that
future identifiers may not be date-shaped:

```python
KNOWN_PROTOCOL_VERSIONS      = ("2024-11-05", "2025-03-26", "2025-06-18", "2025-11-25", "2026-07-28")
HANDSHAKE_PROTOCOL_VERSIONS  = ("2024-11-05", "2025-03-26", "2025-06-18", "2025-11-25")
MODERN_PROTOCOL_VERSIONS     = ("2026-07-28",)
```

"Handshake era" = reachable via `initialize`. "Modern era" = per-request envelope. A version
belongs to exactly one era, so era is derivable from the version string and never has to be
guessed.

## 3. Era detection on stdio

This is the part the specification prose leaves to the implementer and the SDK answers
concretely. From `src/mcp/server/runner.py:602-640` (`serve_dual_era_loop`):

```python
opens_modern = (
    opening is not None
    and opening.method != "initialize"
    and _has_modern_envelope(opening.params)
)
```

> **ADR-016 deliberately diverges from rule 1 below.** adr-kit keeps era a *pure function
> of the single frame* with no era lock and no per-process state. The spec permits a lock
> ("A dual-era server **MAY** serve both eras concurrently"), but a lock means a
> byte-identical frame gets two different answers depending on what arrived earlier on the
> same stdin — which is exactly what *"Servers **MUST NOT** rely on prior requests over the
> same connection to establish context"* forbids. Read rule 1 as what the SDK does, not as
> what adr-kit must do.

Four rules fall out of it, and all four are load-bearing:

1. **The client's first request decides the era, once, for the whole connection.** Not
   per-request. The deciding frame is then replayed into the chosen serving loop.
2. **`initialize` always opens a legacy connection**, even if the client also stamps the
   modern envelope on it — because `initialize` does not exist at 2026 versions at all.
3. **A bare `_meta` is not evidence of the modern era.** Legacy requests legitimately carry
   `progressToken` in `_meta`. Only the presence of the reserved
   `io.modelcontextprotocol/protocolVersion` key is the signal. Verbatim from
   `runner.py:504-517`: *"The `io.modelcontextprotocol/protocolVersion` key exists only in
   2026-07-28+ envelopes and its prefix is spec-reserved, so legacy traffic never mints it."*
4. **A half-built envelope still routes modern**, and then fails with `INVALID_PARAMS`
   naming the missing key — rather than being silently misread as legacy.

Cross-era claims after the era is fixed are refused, not accommodated:

| Situation | Response |
|---|---|
| `initialize` arriving on a modern-locked connection | `-32022` `UnsupportedProtocolVersion`, listing the served versions |
| Enveloped request arriving on a legacy-locked connection | `-32600` `INVALID_REQUEST` |

## 4. The `_meta` keys, verbatim

From `src/mcp-types/mcp_types/_types.py:53-72`:

```python
PROTOCOL_VERSION_META_KEY    = "io.modelcontextprotocol/protocolVersion"
CLIENT_INFO_META_KEY         = "io.modelcontextprotocol/clientInfo"
CLIENT_CAPABILITIES_META_KEY = "io.modelcontextprotocol/clientCapabilities"
LOG_LEVEL_META_KEY           = "io.modelcontextprotocol/logLevel"
SERVER_INFO_META_KEY         = "io.modelcontextprotocol/serverInfo"
```

`protocolVersion` and `clientCapabilities` are the required pair on a modern request; the
SDK validates exactly those two and reports whichever is missing
(`src/mcp/shared/inbound.py:417-420`). `clientInfo` is SHOULD. `serverInfo` is what the
server puts in each result's `_meta` (SHOULD).

## 5. Result shapes

From the authoritative schema (`schema/2026-07-28.json`, `$defs` — note: `$defs`, not
`definitions`).

`CacheableResult` — required: `resultType`, `ttlMs`, `cacheScope`.

`DiscoverResult` — required: `resultType`, `supportedVersions`, `capabilities`, `ttlMs`,
`cacheScope`. Optional: `instructions`, `_meta`. Note that `serverInfo` is *not* a required
top-level field of `DiscoverResult`; server identity travels in `_meta`.

**`supportedVersions` lists modern-era versions only.** The SDK's default handler
(`src/mcp/server/lowlevel/server.py:660-675`) returns `list(MODERN_PROTOCOL_VERSIONS)` —
i.e. `["2026-07-28"]` — not the union with the handshake versions. This follows from
`server/discover` being a modern-era RPC: the list answers "which envelope versions can I
serve", and legacy reachability is decided at the handshake instead. A dual-era server that
advertises `2025-06-18` in `supportedVersions` would be inviting the client to send that
version inside a modern envelope, which is not a thing.

Field semantics worth getting right:

- `resultType` — `"complete"` for ordinary results, `"input_required"` for MRTR interim
  results. Typed as a plain `string` in the schema, not an enum. A client receiving a result
  from an earlier-protocol server that omits the field MUST treat it as `"complete"`.
- `ttlMs` — integer, minimum 0. `0` means "immediately stale". Freshness hint for client
  caching.
- `cacheScope` — enum `"public"` | `"private"`. `"public"` means no user-specific data, so
  shared intermediaries may cache across authorization contexts.

## 6. Error codes

From `src/mcp-types/mcp_types/jsonrpc.py:73-90`, matching the specification's allocation
policy (`-32000..-32019` implementation-defined and grandfathered, `-32020..-32099` reserved
for the specification):

```
-32020  HEADER_MISMATCH                        (HTTP transport only)
-32021  MISSING_REQUIRED_CLIENT_CAPABILITY
-32022  UNSUPPORTED_PROTOCOL_VERSION
-32042  URL_ELICITATION_REQUIRED
-32000  CONNECTION_CLOSED                      (SDK-local, grandfathered range)
-32001  REQUEST_TIMEOUT                        (SDK-local, grandfathered range)
```

Also changed: resource-not-found moved from `-32002` to `-32602` (Invalid Params) to align
with JSON-RPC.

## 7. Backward compatibility is safe in the interim

From the stdio transport page, Backward Compatibility section. A client that supports both
eras SHOULD probe `server/discover` first, and there are exactly three outcomes:

- `DiscoverResult` → server is modern; pick a version from `supportedVersions`.
- A *recognized modern* error such as `UnsupportedProtocolVersionError` → server is modern
  but will not serve the requested version. **Do not fall back to `initialize`.**
- Any other error, or no response within a reasonable timeout → server is legacy; fall back
  to `initialize`.

And, verbatim: *"The fallback MUST NOT be keyed to one specific error code: legacy servers
respond to unknown pre-`initialize` requests with implementation-defined errors (commonly
`-32601` or `-32602`) or not at all."*

**Consequence for adr-kit:** today's `bin/adr-mcp` answers `server/discover` with `-32601`,
so a new client correctly classifies it as legacy and falls back. The server is
non-compliant, not broken. That sets the urgency, and it is why this work is a planned
change rather than an incident.

## 8. The hazard that is real today

The same section warns why a legacy server should still be reachable deterministically:

> A client that only supports modern versions does not need to probe, but probing is still
> **RECOMMENDED**: some legacy servers do not validate that a request arrives after
> `initialize` and would process an era-ambiguous method (such as `tools/call`) under legacy
> semantics. Probing yields a deterministic failure instead.

`bin/adr-mcp` is exactly such a server: `dispatch()` never checks that `initialize` came
first. A modern-only client that skips the probe gets silent legacy behaviour.

## 9. What does *not* apply to a stdio, tools-only server

Most of the revision. Recording this explicitly so a future reader does not mistake it for
an oversight:

| Change | Why it does not apply |
|---|---|
| `Mcp-Session-Id` removal, `subscriptions/listen`, `Last-Event-ID` removal, GET endpoint removal, `Mcp-Method`/`Mcp-Name` headers, `x-mcp-header`, `HeaderMismatch` `-32020` | All Streamable HTTP transport mechanics. adr-mcp is stdio-only. |
| MRTR / `InputRequiredResult` / `inputRequests` | The server never needs input from the client; it wraps read-only CLIs. It never initiated `sampling/createMessage`, `roots/list` or `elicitation/create` in the first place. |
| Tasks extension (`io.modelcontextprotocol/tasks`) | Opt-in extension; the five tools are short-running and synchronous. |
| Roots, Sampling, Logging deprecations (SEP-2577) | None of the three were ever implemented. |
| `resources/*`, `prompts/*` cacheable-result requirements | No resources, no prompts. Only `tools/list` is affected. |
| `logging/setLevel` removal, `io.modelcontextprotocol/logLevel` | No logging feature. Diagnostics already go to `stderr`, which the stdio page explicitly permits. |
| `ping` removal | Trivially: stop advertising it in the modern era, keep it in the legacy era. |

## 10. SDK adoption cost, for the record

Facts gathered while reading, relevant to the alternative the ADR rejects:

- `mcp` 2.0.0 released 2026-07-28 — the same day as the specification revision.
- `requires-python >=3.10`. adr-kit's CI test matrix is `['3.10', '3.12']`
  (`.github/workflows/validate.yml:175`), so the floor is compatible — this is *not* an
  argument against adoption.
- `project.dependencies` is declared `dynamic`, resolved from `uv.lock`; it is not a
  dependency-free package. The server surface imports `anyio` (`runner.py` uses
  `anyio.Event`) and the types layer is Pydantic-based (`model_dump(mode="json")`).
- The package is split into two distributions, `mcp` and `mcp-types`.
- It is a deliberate rewrite: the release describes itself as *"a major rework of the SDK,
  both to support the 2026-07-28 MCP specification (and every earlier revision)"*, with a
  dedicated 1.x→2.0 migration guide.
